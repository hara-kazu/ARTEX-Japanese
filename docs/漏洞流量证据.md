# 脆弱性の複数トラフィック証拠

脆弱性の詳細の「関連トラフィック」では、ページをまたぐ複数選択、用途と説明の設定、並べ替え、関連付けの解除ができます。トラフィックページでも複数の記録を選択し、既存の一件の脆弱性にまとめて関連付けられます。タスクが継承した脆弱性の証拠は読み取り専用で、変更するには元のタスクに移動する必要があります。

システム設定の「Agent によるトラフィックの自動関連付け」は標準でオフです。読み取りと変更には `/api/settings` の `agent_traffic_binding` を使用します。オンにすると、リクエスト / レスポンスの確認、ツール呼び出し、プロンプトによる Token 消費量が増えます。新しい設定は次の Agent のラウンドから使用します。オフにすると、自動関連付けのパラメーターと追加関連付けツールを非表示にし、自動関連付けの指針を挿入せず、実行中のセッションから新たに送信された自動関連付けも拒否します。手動での関連付け、トラフィックのキャプチャ、保存済みの証拠の読み取りとエクスポートには影響しません。

オンにした場合の標準の流れは「検出結果を保存 → レポート Agent を自動起動 → トラフィックを確認して関連付け → 最新の証拠バージョンに基づいてレポートを作成」です。報告者は `evidence` に検証コマンド、主要な出力、既存の実在するトラフィック ID と用途を残します。レポート Agent は脆弱性の詳細と実行記録を合わせて確認し、`traffic_search` / `traffic_get` で検証してから `bind_finding_traffic` を呼び出し、最新の `version` を読み取ってレポートを保存します。オフの場合、レポート Agent に生のトラフィックの検索 / 読み取りツールを追加で与えず、自動関連付けも行いません。手動で関連付けたスナップショットの読み取りとレポート生成は引き続き可能です。

既存の呼び出し元との互換性：`report_finding` の `traffic_refs` / `evidence_hint_id` による明示的な即時関連付けは引き続き使用できます。関連付けは任意です。TCP などの HTTP 以外の脆弱性、未収集の場合や正確な記録が見つからない場合は、参照を省略しても通常どおり報告とレポート作成ができます。コマンド出力やログなど、ほかの検証可能な証拠を残し、関連付けていない理由の説明を推奨しますが、必須項目は追加しません。送信する ID はすべて有効で、本文が完全である必要があります。一件でも失敗すると、その関連付け操作全体をロールバックします。報告時の明示的な関連付けが失敗した場合は、報告全体をロールバックします。同じスナップショットを重複して追加しても関連付けを増やさず、説明も上書きしません。

## Agent の番号とレポートのバージョン

`report_finding` に任意のパラメーターを追加します。配列の順序が初期の証拠の順序になります：

```json
{
  "traffic_refs": [
    {"traffic_id": "実在するトラフィックID", "role": "baseline", "note": "通常のアカウントのリクエスト"},
    {"traffic_id": "別の実在するトラフィックID", "role": "proof", "note": "再現リクエスト"}
  ]
}
```

用途は `baseline`（正常時との比較）、`proof`（脆弱性の証明）、`verification`（追加の検証）、`supporting`（補助証拠、標準）です。先に `traffic_search` / `traffic_get` で実際の記録を確認してください。ドメインと時刻は候補の絞り込みだけに使い、タスクへの所属は推定しません。

プロンプトは [CyberStrikeAI の脆弱性報告ツールの指針](https://github.com/RuoJi6/CyberStrikeAI/blob/54d56774b8bd285817d16d48b70a4a5e6e0963f7/internal/app/vulnerability_tools.go)を参考にし、このプロジェクトの任意の関連付けに関する取り決めと組み合わせています。パケットがない理由を必須にする検証は導入しません。ID を推測したり、パケットを補うことだけを目的に再度探索したりしてはいけません。

戻り値の一行目は引き続き `finding recorded: <探索ノード ID>` です。続く JSON は、独立した脆弱性レコードの `finding_id`、探索ノードの `finding_node_id`、関連付けの概要を提供します。

- `get_finding_traffic(finding_id)` は**独立した脆弱性レコードの ID**を使い、順序付きの一覧と `version` を返します。`binding_id`、`side=request|response`、`offset`、`length` を渡すと分割して読み取れます。各部分は最大 8192 バイトです。
- `update_finding_report` の `finding_id` は**引き続き探索ノード ID を使用します**。追加の `evidence_version` には、実際に読み取ったバージョンを指定します。生成中に証拠が変わった場合は古いバージョンでの書き込みを拒否するため、再度読み取って生成する必要があります。
- 古いレポート呼び出しでバージョンを渡さなかった場合、既存のトラフィック証拠を網羅しているとは表明しません。関連付け、説明、用途、順序が変わると、既存のレポートに更新が必要であることを表示します。

自動関連付けをオンにすると、`add_hint` / `add_task_hint` で単一のヒント、または一括指定の `hints` の各要素に `traffic_refs` を保存できます。Planner が代わりに報告する場合は `evidence_hint_id` を渡し、このタスクの対応するヒントから参照を明示的に選択できます。継承したヒントは参照できません。システムはドメイン、時刻、閲覧記録から関連付けを推測しません。送信に失敗した場合、脆弱性の一部だけを生成したり、先にレポートを起動したりしません。

既存の脆弱性に関連付け漏れがある場合は、`bind_finding_traffic(finding_id, traffic_refs)` で追加関連付けでき、重複して登録する必要はありません。`list_findings` / `list_task_findings` / `node_detail` / `get_task_node_detail` は明示的な `finding_id` と `finding_node_id` を返します。旧 `id` は引き続き探索ノードを意味します。

起動時は既存ツールの schema に任意の属性だけを追加し、生のトラフィックツールの標準の割り当てをレポート Agent にも拡張します。追加関連付けツールは標準でレポート Agent に渡します。カスタムの割り当て一覧、プロンプト、説明、有効化状態は保持します。指針は最終的なツールの組み立て後にまとめて追加します。報告役は既存の証拠の引き継ぎを担当し、レポート Agent は確認、関連付け、レポート作成を担当します。プラットフォームのチャットにタスクのコンテキストがない場合、直接報告せず、構造化したヒントを通じてタスク Agent に引き継ぐ必要があります。タスクの完了を判定する前に、先に既存の証拠を引き継ぐ必要があります。パケットがない場合は待機を強制しません。失敗した `report_finding` はレポート Agent を起動しません。

## API

基本パス：`/api/exploration/findings/{finding_id}/traffic`。独立した脆弱性 ID を使用します。認証は既存の仕組みを使い、`context_task` でタスクの可視性と継承による読み取り専用を検証します。

| メソッド / 相対パス | リクエスト / 戻り値 |
| --- | --- |
| `GET` | 順序付きの概要、証拠のバージョン、レポートで使用したバージョン |
| `POST` | `{"traffic_refs":[...]}` を一括で追加 |
| `PATCH /{binding_id}` | `{"version":1,"role":"proof","note":"説明"}` |
| `DELETE /{binding_id}` | `{"version":1}` |
| `PUT /order` | `{"version":1,"binding_ids":["2","1"]}`。完全な一覧である必要があります |
| `GET /{binding_id}` | スナップショットのメタデータと長さを制限した本文のプレビュー |
| `GET /{binding_id}/body` | `side`、`offset`、`length`。`download=1` で元のバイト列全体をダウンロード |

バージョン / 並べ替え対象の集合の競合、アーカイブ中の書き込みは `409`、継承した内容への書き込みは `403`、存在しないか脆弱性に属さない関連付けは `404` を返します。トラフィック / 添付ファイルの読み取りや検証に失敗した場合は、明示的にエラーを返します。

## 保存と移行

起動時に PostgreSQL の冪等な移行を行います。`traffic_evidence_snapshots`、`finding_traffic_bindings`、および `findings.evidence_version` / `report_evidence_version`（標準は 0）を追加します。過去の文章から推測して追加関連付けは行いません。

スナップショットには元のトラフィック ID、収集時刻、URL、メソッド、ステータス、リクエスト / レスポンスヘッダー、本文の長さ、SHA-256 を保存します。本文はハッシュに基づいて `<data>/evidence/blobs/<先頭二文字>/<hash>.bin` に保存し、削除可能な `data/traffic` から独立させます。複数の脆弱性でスナップショット / 本文を共有できます。スナップショットには内容を更新するインターフェースを用意せず、検証が一致しなければ読み取りとエクスポートに失敗します。

元のトラフィックの書き込みロックの下で、大きな本文の blob や旧ディレクトリの記録も含めて本文全体を読み取ります。先にファイルを永続化して検証し、次に単一の PostgreSQL トランザクションで探索ノード、インテントの関係、脆弱性、スナップショット、関連付けを書き込みます。コミット後に初めてプランナーに通知します。失敗すると参照のないファイルが残ることはありますが、業務レコードの一部だけが生成されることはありません。

PostgreSQL advisory lock `7337741004` で証拠ファイルと SQL の参照を調整します。タスクの行ロックにより、アーカイブのキューに入った後の証拠の変更を禁止します。復元では本文の配置からメタデータのコミットまで、全体を通して証拠ロックを保持します。脆弱性を削除すると、関連付けも連鎖的に削除します。

クリーンアップは毎時実行し、参照がなく処理中の操作に含まれない内容だけを、少なくとも 24 時間待ってから回収します。通常のトラフィックのクリーンアップは証拠ディレクトリに触れません。ホットデータをバックアップする場合は、PostgreSQL と `data/evidence` を同時にバックアップしてください。

## エクスポートとアーカイブ

Markdown には順序付きの証拠一覧とバージョン、JSON にはメタデータを含めます。CSV には件数と関連付け ID を追加します。`md-zip` は脆弱性の Markdown を保持し、次を提供します：

```text
evidence/<finding_id>/<binding_id>/
  manifest.json
  request.http
  response.http
  request.bin
  response.bin
```

Markdown は相対リンクでリクエスト / レスポンスを参照します。ダウンロードを送信する前に、添付ファイルのコピー、ハッシュ検証、圧縮、ディスクへの同期、すべての ZIP エントリーの CRC 読み取り検証を完了します。欠落 / 破損があればダウンロード全体を失敗させます。完全な添付ファイルは、バイナリの元のバイト列を保持します。

アーカイブ v3 は、元のトラフィックやドメインに依存せず、脆弱性の関連付けに基づいてスナップショットと本文を収集します。パッケージの検証が完了してからホットデータを削除し、共有している証拠は保持します。復元では先に本文を検証して配置し、次にトランザクションでメタデータと関連付けを復元します。失敗時の再試行に対応します。v1/v2 も引き続き復元でき、不足している新しいフィールドには明示的に 0 を補います。

## 検証と制限

テストパッケージごとに独立した新規の PostgreSQL テストデータベースを用意し、`ARTEX_PG_DSN` で指定してください。残存するタスク / モデルのフィクスチャによる背景実行を避けます。関連パッケージのテスト全体を実行し、設定不足によるスキップがないことを確認してください：

```sh
# 各パッケージの実行前に ARTEX_PG_DSN を対応する独立したテストデータベースに設定します。明示的な設定が失敗した場合は必ずエラーにします。
go test ./<package> -count=1
go test -race -p 1 ./evidence ./db ./agent ./server -run 'TestEvidence|TestFindingTraffic|TestFindingEvidence|TestReportFindingAtomicContract|TestTaskArchive'
```

フロントエンドの検証には、`npx tsc --noEmit`、影響を受けるファイルの Biome チェック、Webpack ビルド、`NEXT_EXPORT=1` による静的出力を含めます。実行中の開発サービスを上書きしないよう、独立したキャッシュディレクトリを使用してください。

ローカルでのエンドツーエンド検証では、独立したポート、制御下の HTTP / ドメインの HTTPS の対象、一時データディレクトリを使用します。二つの関連付けの入口、ページをまたぐ選択、並べ替え / 説明、エラー表示、継承による読み取り専用、ダウンロード、元のトラフィックを削除した後のエクスポート、アーカイブ、ホット本文の回収、復元、ハッシュ検証を確認します。

初版では全体共通の証拠調整ロックを使用します。大量の関連付け / エクスポートや、添付ファイルのダウンロードが遅い間は、ほかの証拠操作が待機する場合があります。記録や完全な本文がない場合、証拠を捏造して補うことはできません。この機能はキャプチャの切り替えを変更せず、HTTPS で IP に直接アクセスする際の証明書の問題も扱いません。
